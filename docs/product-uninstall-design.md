# 製品アンインストール設計

## 目的

この資料は、Timeline の製品管理における「アンインストール」の意味を整理するための設計メモです。

アンインストールを単純な「全部削除」として扱うと危険です。ユーザーがやりたいことは、状況によって異なります。

- 今はその製品を使わないようにしたい
- アプリ本体を消して容量を空けたい
- 後で再インストールする可能性があるので設定は残したい
- 生成済みデータやマスターデータは再利用したい
- できるだけ関連データも含めて削除したい

そのため、画面では以下を明確に見せる必要があります。

- 何が削除されるのか
- 何が残るのか
- どのくらい容量が空く見込みか
- 後で再インストールした場合にどうなるのか

## 用語

### 起動

起動とは、対象製品の起動スクリプトを実行することです。

```text
start.ps1
```

### 停止

停止とは、対象製品の停止スクリプトを実行することです。

```text
stop.ps1
```

ユーザー向けには「製品の Docker ワーカー / ローカル実行環境を停止する」と説明してよいです。

Timeline は、サブ製品の Docker コンテナ内に入ったり、サブ製品の Docker を推測で直接操作したりしません。起動・停止は、対象製品が提供する `start.ps1` / `stop.ps1` を使います。

### アンインストール

アンインストールでは、必ず対象製品のアプリケーションディレクトリを削除します。

例:

```text
C:\apps\TimelineForAudio
C:\apps\TimelineForImage
C:\apps\TimelineForVideo
```

Docker 関連の削除は、Timeline 側がその製品に対する明示的な製品管理契約を持っている場合にだけ行います。Docker のリソース名を Timeline が推測して削除したり、サブ製品単体用のアンインストール処理に依存したりしません。

この製品管理契約は、将来的には各サブ製品のルート直下に置く `timeline-product.json` で表現します。詳細は `docs/timeline-product-manifest.md` を参照します。

## サブ製品の uninstall.ps1 は Timeline から使わない

一部のサブ製品には、すでに `uninstall.ps1` が存在します。

例:

```text
C:\apps\TimelineForAudio\uninstall.ps1
C:\apps\TimelineForWindowsCodex\uninstall.ps1
```

ただし、Timeline 管理のアンインストールでは、これらの `uninstall.ps1` は呼びません。

これらのスクリプトは、サブ製品を単体で使っているユーザー向けです。たとえば Timeline を使わずに `TimelineForAudio` や `TimelineForWindowsCodex` を直接使っている場合には、その製品自身のアンインストール手段として意味があります。

しかし、Timeline の製品管理から見ると、`uninstall.ps1` は適切な制御面ではありません。

理由:

- Timeline 側で確認画面を一貫して管理したい
- 設定を残すか削除するかを Timeline 側で決めたい
- 生成済みデータ / マスターデータを残すか削除するかを Timeline 側で決めたい
- 削除される容量を Timeline 側で見積もって説明したい
- 製品アプリケーションディレクトリの削除を Timeline 側で制御したい
- サブ製品ごとに `uninstall.ps1` のオプション名や意味が揃っていない可能性がある
- 実行中のスクリプトが存在するディレクトリ自体を削除する設計は壊れやすい
- 製品ごとの `uninstall.ps1` に依存すると、Timeline のアンインストール挙動が製品ごとに揺れる

責務分担は以下のようにします。

| 対象 | 責務 |
|---|---|
| サブ製品の `uninstall.ps1` | サブ製品を単体で使うユーザー向けのアンインストール手段 |
| Timeline の製品管理 | 製品停止、設定の退避 / 削除、マスターデータの保持 / 削除、Docker 関連の削除、製品アプリケーションディレクトリ削除、確認画面、復元案内、操作ログ |

つまり、`uninstall.ps1` が存在していても Timeline からは無視します。

Timeline は、すべてのサブ製品に対して同じ Timeline 管理のアンインストールフローを使います。Docker 関連の削除を安全に実行できない場合は、サブ製品の `uninstall.ps1` をフォールバックとして呼ぶのではなく、「Docker 関連の削除は未確認」と画面に表示します。

サブ製品を直接使うユーザーは、その製品自身の `uninstall.ps1` を使って構いません。Timeline 管理のアンインストールは、それより広い操作です。設定退避、再インストール時の復元、Timeline 側の記録、製品配置、統一された確認画面まで含めて管理します。

## アンインストールで必ず削除するもの

以下はアンインストールそのものに含めます。

- 製品アプリケーションディレクトリ
- 製品のソースファイル
- 製品の起動・停止スクリプト
- 製品ローカルの Docker Compose ファイル
- 製品ディレクトリ内のビルド成果物やキャッシュ
- Timeline が明示的に把握している、その製品専用の Docker 関連リソース

Docker 関連リソースを安全に削除できない場合は、アプリ本体は削除できたが Docker 関連の削除は確認できていない、という状態を画面に表示します。

## 通常アンインストールでは削除しないもの

通常のアンインストールでは、以下は削除しません。

- ユーザーの元ファイル
  - 音声ファイル
  - 動画ファイル
  - 画像ファイル
  - ChatGPT のエクスポート ZIP
  - Codex の元ログ
- Timeline 本体
- Timeline 全体の基本設定
- Timeline の操作ログ

元ファイルの削除は、アンインストールに含めません。元ファイルを削除する操作が必要な場合は、別の危険操作として分けます。

## ユーザーが選択できる項目

アンインストールボタンを押したら、すぐ削除せず、確認フローを表示します。

### 設定を残す

表示名:

```text
設定を残す
```

意味:

- 再インストール時に使い回せるよう、製品設定を退避または保持する
- 設定ファイルが製品ディレクトリ内にある場合は、製品ディレクトリ削除前に Timeline 管理の退避先へ移す

推奨初期値:

```text
ON
```

理由:

多くのユーザーは、設定を失いたいわけではなく、一時的に使わない、または再インストールしたいだけの可能性が高いためです。

### 取り込んだデータを残す

表示名:

```text
取り込んだデータを残す
```

意味:

- 製品のマスター / 出力ディレクトリを残す
- Timeline 側に取り込まれたその製品由来の記録を残す
- 再インストール後に再利用できる可能性がある生成物を残す

推奨初期値:

```text
ON
```

理由:

生成済みデータは再作成に時間がかかる可能性があります。残しておく方が、再インストール時の復帰がしやすいです。

### 取り込んだデータも削除する

表示名:

```text
取り込んだデータも削除する
```

意味:

- その製品が生成したマスター / 出力 / 生成済みデータを削除する
- 再利用できなくなる Timeline 側の取り込み記録も削除対象にする
- ただし、ユーザーの元ファイルは削除しない

推奨初期値:

```text
OFF
```

理由:

これは破壊的な操作です。明示的に選んだ場合だけ実行します。

### 設定も削除する

表示名:

```text
設定も削除する
```

意味:

- 再インストール用の設定退避を作らない
- 既に Timeline 側に退避されているその製品の設定も削除する

推奨初期値:

```text
OFF
```

理由:

設定は容量が小さく、復帰時に役立つ可能性が高いためです。

## 容量見積もり

最終確認前に、どのくらい容量が空く見込みかを表示します。

推奨カテゴリ:

| 表示名 | 意味 |
|---|---|
| アプリ本体 | 製品アプリケーションディレクトリの容量 |
| Docker 関連 | Timeline が把握している製品専用 Docker リソースの容量 |
| 設定 | 設定ファイルや退避設定の容量。通常は小さい |
| 生成データ | 製品のマスター / 出力 / 生成済みデータの容量 |
| Timeline 記録 | Timeline 側の記録。容量削減としては通常大きくない |

表示例:

```text
削除すると、約 12.4 GB の空き容量が増える見込みです。

内訳:
- アプリ本体: 1.2 GB
- Docker 関連: 8.6 GB
- 生成データ: 2.6 GB
- 設定: 1 MB 未満
```

見積もれない項目は、隠さずに次のように表示します。

```text
未確認
```

不確かな値を無理に確定したように見せないことが重要です。

## 実行計画

アンインストールを実行する前に、必ず内部で実行計画を作成します。

実行計画には、最低限以下を含めます。

- 製品 ID
- 製品名
- 製品アプリケーションディレクトリ
- 設定ファイルの場所
- 設定を退避するか
- 設定の退避先
- 生成済みデータ / マスターデータの場所
- 生成済みデータ / マスターデータを削除するか
- 削除予定容量
- 未確認項目

画面では、この実行計画を人間が分かる形に変換して表示します。

実行計画に含まれていないパスは削除してはいけません。

## 設定退避と秘密情報

設定ファイルには、Hugging Face トークンなどの秘密情報が含まれる可能性があります。

そのため、「設定を残す」は便利ですが、単なる小さな設定ファイルとして扱ってはいけません。

最低限、次の前提で扱います。

- 設定退避先は製品アプリケーションディレクトリの外に置く
- 設定退避先は Timeline が管理する場所に限定する
- 画面では「設定にはトークンなどが含まれる場合があります」と説明する
- 操作ログにはトークン本体を書かない

将来的には、設定ファイルの中から秘密情報だけを OS の資格情報ストアへ移すことも検討します。

## Docker 関連削除の扱い

Timeline は、Docker リソース名を推測して削除しません。

Docker 関連を削除する場合は、Timeline 側の製品管理情報に明示されたものだけを削除します。

例:

```json
{
  "id": "audio",
  "docker": {
    "composeProject": "timeline-for-audio",
    "volumes": [
      "timeline-for-audio_app-data",
      "timeline-for-audio_cache-data"
    ],
    "images": [],
    "networks": []
  }
}
```

このような明示情報がない場合、Docker 関連は削除しません。

その場合、画面には次のような表示を出します。

```text
Docker 関連の削除は未確認です。
製品アプリ本体は削除できますが、Docker 側の一部データが残る可能性があります。
```

## 起動中の製品をアンインストールする場合

対象製品が起動中の場合は、いきなり削除しません。

流れ:

1. 製品が起動中であることを表示する
2. アンインストール前に停止が必要であることを伝える
3. `stop.ps1` を実行する
4. 停止に成功した場合だけアンインストールを続行する

表示例:

```text
この製品は現在起動中です。
アンインストールする前に停止します。

停止に失敗した場合、削除は実行しません。
```

製品が起動中と判断されている間は、削除を実行しません。

## 確認フロー

### 1. 削除範囲を選ぶ

タイトル例:

```text
TimelineForAudio をアンインストールしますか？
```

本文例:

```text
アンインストールすると、製品アプリ本体は削除されます。
元の音声・画像・動画ファイルは削除されません。
```

操作項目例:

```text
[x] 設定を残す
[x] 取り込んだデータを残す
[ ] 取り込んだデータも削除する
[ ] 設定も削除する
```

「取り込んだデータを残す」と「取り込んだデータも削除する」は同時に成立しないため、実装上はラジオボタンにした方がよいです。

推奨:

```text
取り込んだデータ:
(*) 残す
( ) 削除する
```

設定についてはチェックボックスでよいです。

```text
[x] 設定を退避して残す
```

### 2. 実行内容をプレビューする

最終確認前に、何が起きるかを具体的に表示します。

表示例:

```text
実行内容

削除する:
- 製品アプリ本体
- 製品専用の Docker 関連データ

残す:
- 元の音声ファイル
- 生成済みデータ
- Timeline の記録
- 設定の退避データ

再インストールした場合:
- 退避した設定を利用できます
- 前回の生成データを再利用できます
```

### 3. 最終確認する

タイトル例:

```text
この処理を実行しますか？
```

本文例:

```text
製品アプリ本体は削除されます。
選択した内容に従って、設定と取り込んだデータを残すか削除します。
```

ボタン例:

```text
キャンセル
アンインストールする
```

生成済みデータも削除する場合は、より強い文言にします。

```text
データも削除してアンインストールする
```

## 再インストール時の復元

製品を再インストールする時、Timeline は過去の利用情報を検知します。

### 退避した設定が見つかった場合

表示例:

```text
前回退避した設定があります。
この設定を使って再インストールしますか？
```

推奨初期値:

```text
使う
```

### 前回取り込んだデータが見つかった場合

表示例:

```text
前回取り込んだデータが見つかりました。
再インストール後もこのデータを使いますか？
```

推奨初期値:

```text
使う
```

### 設定とデータの両方が見つかった場合

別々のダイアログを出すより、1つの復元画面にまとめます。

表示例:

```text
前回の利用情報が見つかりました。

[x] 退避した設定を使う
[x] 前回取り込んだデータを使う
```

## 退避先

設定の退避データは、製品アプリケーションディレクトリの外に置きます。

例:

```text
C:\TimelineData\Timeline\backups\products\<product-id>\settings\
C:\TimelineData\Timeline\backups\products\<product-id>\metadata.json
```

生成済みデータ / マスターデータは、ユーザーが削除を明示的に選ばない限り、既存のマスター / 出力ディレクトリに残します。

## 製品ごとに必要な管理情報

このアンインストールを安全に実装するには、Timeline が各製品について次の情報を持つ必要があります。

- 製品アプリケーションディレクトリ
- 設定ファイルの場所
- 製品のマスター / 出力ディレクトリ
- 生成済みデータのディレクトリ
- Timeline が削除してよい製品専用 Docker リソース
- 各カテゴリの容量、または容量計測に使えるパス

危険なパスを Timeline が推測して削除してはいけません。

## 推奨実装ステップ

段階的に実装します。

### ステージ 1

- アンインストールでは必ず製品アプリケーションディレクトリを削除する
- 起動中なら `stop.ps1` で停止してから削除する
- 設定ファイルの場所が分かる場合は、初期状態では退避する
- 生成済みデータ / マスターデータは初期状態では残す
- 元ファイルは絶対に削除しない
- アプリ本体ディレクトリの容量を表示する

### ステージ 2

- 生成済みデータ / マスターデータを削除する選択肢を追加する
- 設定も削除する選択肢を追加する
- 再インストール時の復元確認を追加する
- 生成済みデータ / マスターデータの容量見積もりを追加する

### ステージ 3

- Timeline 側の明示的な製品管理契約に基づいて Docker 関連リソースを削除する
- Docker 関連容量が分かる場合は表示する
- 各アンインストール工程を操作ログに残す

## 現在の実装との差分

現在の実装は、主に次の確認後に製品アプリケーションディレクトリを削除する作りです。

- 製品が起動中ではないこと
- 削除対象が Timeline 本体ではないこと
- 削除対象がドライブ直下ではないこと
- 削除対象が Timeline サブ製品らしいこと
- Git 作業ツリーがクリーンであること

追加済み:

- アンインストール実行計画の作成
- 設定を退避して残す選択
- 生成済みデータ / マスターデータを残すか削除するかの選択
- 容量見積もりのプレビュー
- 再インストール時に退避済み設定を自動復元する処理
- テスト用製品ディレクトリを使ったスモークテスト

まだ不足しているもの:

- 再インストール時の復元確認 UI
- Docker 関連リソース削除の明示的な製品管理契約
- Docker 関連リソースの容量見積もり
- Git 作業ツリー確認を開発モード限定にする整理
