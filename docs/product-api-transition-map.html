API transition map

Timeline サブ製品 API 移行整理

CLI 中心の入口を、各サブ製品のローカル API 契約へ移すための設計メモです。 目的は API 名を増やすことではなく、現行 CLI の責務を確認したうえで、変えるものと維持するものを管理し、 ユーザーに見せる操作を「状態確認」「設定」「更新」「記録」「元データ」「ダウンロード」に揃えることです。

読み方

各 API は階層構造で整理しています。親の共通 API を全製品が持ち、製品ごとの差分は「ファイル」「会話」「PC記録」などの追加枝として扱います。 実装上の継承を強制する資料ではありませんが、Swagger と後続アプリケーションで契約が揺れないよう、概念上の親子関係を固定します。

ここでの API は設計案から実装方針へ移行しています。現行実装は各サブ製品のローカル API と Timeline helper の HTTP API を中心に整理しています。
1. 基本判断現行入口、クラス概念、変更/維持の管理 1.1 現状整理CLI / helper / Docker / PC の責務境界 1.2 クラス概念共通親、ファイル系、会話系、PC記録系 1.3 移行管理変えるもの、維持するもの、理由 2. 全製品共通 APIヘルス、状態、設定、更新、記録 3. 製品グループ別 APIファイル系、会話系、PC記録系 4. 製品別の現行対応現在の CLI / UI との対応 5. 長時間処理の扱い進捗、キュー、キャンセル、復旧 6. あるべき配慮入れる、予約する、入れないを分ける 7. 返却形式Swagger 化で共通化する形

1. 基本判断

共通化するもの

ユーザーの操作名は揃えます。状態確認、設定、更新、記録一覧、ダウンロード、処理履歴は全製品で同じ言葉にします。

差分にするもの

元データの形だけを差分にします。音声・画像・動画はファイル、ChatGPT と WindowsCodex は会話、PC は PC記録です。

残すもの

`start.ps1` / `stop.ps1` は Docker やローカル実行環境の起動停止として残します。CLI は API を叩く運用ラッパーに降格できます。

API の URL は開発者向けには英語ですが、画面表示では「records = 記録」「tasks = 処理」「sources = 元データ」「conversations = 会話」のように日本語名を併記します。
判断 採用する形 理由
製品別に `items refresh` を分けるか POST /refresh に統一 ユーザーにとっては全製品とも「最新状態に更新する」です。差分はリクエスト本文と内部処理に閉じ込めます。
`items` という語を前面に出すか /records を正面にし、内部で item と対応 一般ユーザーには「記録」の方が分かりやすいです。既存成果物の item id は互換情報として残せます。
ヘルスを分けるか /health と /status を分ける /health は機械監視用、/status は画面表示用です。用途が違うため返す情報も分けます。
ChatGPT と WindowsCodex を別概念にするか 両方 /conversations を持つ会話系にする どちらも会話スレッドの一覧・詳細・メッセージ・タイムラインを扱うためです。ChatGPT の ZIP だけ /imports として追加します。
TimelineForPC をファイル系に寄せるか /captures を持つ PC記録系にする PC は元ファイルを変換するのではなく、その時点のPC状態を記録します。ファイル一覧や会話一覧とは本質が違います。

1.1 現状整理

現在は「単体製品の入口」と「Timeline Web からの入口」が分かれています。 単体製品では CLI が正式入口で、Timeline Web では C# Local API が HTTP を受けて CLI / 既存出力 / 設定ファイルを読んでいます。 API 化では、この二重構造をいきなり壊すのではなく、外部契約を Local API に固定し、内部実装として既存 CLI / PowerShell 関数を段階的に使い続けます。

現行の入口 現在の責務 完成版での扱い 理由
start.ps1 / stop.ps1 Docker worker、ローカル実行環境、補助サーバーの起動停止。 維持 実行環境のライフサイクル操作として残す。 起動停止は API の業務操作ではなく、Docker / host runtime に対する運用操作だからです。
ホストCLIランチャー 旧単体製品の正面入口。 変更 UI の正面入口から外し、ローカル API に置き換える。 Web UI、ヘルスチェック、複数アクセス、進捗確認は CLI 標準出力より HTTP API の方が安定して扱えるためです。
Timeline helper の /products/{id}/... 現行 Web UI 用の薄い HTTP API。裏側で CLI や既存出力を読む。 変更 将来のサブ製品 API の互換アダプター、または親製品の集約 API として整理する。 既に画面は HTTP を使っているため、ここを根拠に Swagger 契約へ移すのが最も現実的です。
Docker worker Audio / Image / Video / ChatGPT / WindowsCodex の実処理を担当。 維持 処理基盤として残し、API は worker の状態と処理受付を公開する。 重い処理や依存関係を Docker に閉じ込める設計は妥当です。API 化は入口の整理であり、処理基盤の否定ではありません。
TimelineForPC の host CLI Windows host の実機情報を読む。Docker ではない。 維持 Docker 化せず、Windows host API または host CLI アダプターとして扱う。 PC 状態の取得はコンテナ内では正しくできないためです。PC はファイル系ではなく PC記録系として別枝にします。
重要な前提: API 化は「全製品を同じ実装にする」ことではありません。揃えるのは契約、用語、状態管理、エラー、長時間処理の扱いです。 Docker worker、host 実行、ZIP 取り込み、ローカル履歴読み取りといった実装差は、製品ごとの派生責務として残します。

1.2 設計上のクラス概念

実際に C# の継承として実装する前提ではありません。Swagger、DTO、UI クライアント、設計レビューで使う概念上の親子関係です。 子製品は親の責務を勝手に再定義せず、必要な枝だけを追加します。

責務

ヘルス、状態、設定、処理、記録、ダウンロード、エラー、データ鮮度、製品能力を共通化します。

対象製品
Audio / Image / Video / PC / ChatGPT / WindowsCodex
共通 API
/health, /status, /settings, /settings/check, /refresh, /tasks, /records, /records/download, /records/generated, /capabilities
守ること
共通レスポンス、ページング、長時間処理、ユーザー向けエラー、ログマスク、元データ保護。

継承元

BaseProductApi

対象製品

追加 API
/sources, /files, /files/{fileId}, /files/{fileId}/source
維持する思想
元ファイルは読み取り専用。ZIP には原則として元ファイルを含めず、生成物だけを扱う。
派生差分
Audio は音声モデルと話者/時間、Image は OCR と画像メタデータ、Video は ffprobe / フレーム / OCR / 音声 / 活動マップを持つ。

継承元

BaseProductApi

CaptureProductApi: その時点の状態を記録する製品

継承元

BaseProductApi

対象製品
TimelineForPC
追加 API
/captures, /captures/{captureId}, /captures/{captureId}/report, /captures/{captureId}/snapshot
別個にする理由
PC は「元ファイルを変換する」製品ではなく、「現在の Windows host 状態を記録する」製品です。ファイル系に寄せると責務がずれます。

ProductManagementApi: 親 Timeline 側の別責務

継承させないもの

インストール、アンインストール、製品登録、起動停止、実行環境データの扱いは、サブ製品 API の親クラスには入れません。

対象
Timeline 本体の製品管理。timeline-product.json、製品カタログ、runtime status、uninstall plan。
理由
製品自身の記録操作と、親 Timeline が製品を管理する操作は危険度も責務も違うためです。
維持する境界
Timeline はサブ製品の Docker 名を推測で直接操作せず、製品が提供する launcher / manifest / 契約に従う。

1.3 変更/維持の管理表

CLI の挙動を一気に変えると、後続アプリケーションが混乱します。 そのため、変更するところ、維持するところ、予約だけするところを以下の表で固定します。

対象 現行 判断 完成版 API 理由
画面からの操作入口 Timeline helper または CLI 呼び出し。 変更 Web UI は HTTP API を正面入口にする。 ヘルス、進捗、複数アクセス、エラー表示、再試行を統一するため。
単体運用の CLI ローカル API が正式入口。 変更 ホストCLIランチャーは廃止し、検証スクリプトも API を直接確認する。 複数アクセス、進捗確認、エラー表示、UI 統合を安定させるため。
overview Timeline helper の製品別画面状態。 変更 /status 一般語として「状態」に統一し、画面表示用であることを明確にするため。
items 生成済み成果物の内部単位。 変更 /records 一般ユーザーには「記録」の方が理解しやすい。内部 item id は互換IDとして保持する。
runs 製品ごとの診断/処理履歴。 変更 /tasks Web UI では「いま走っている処理」と「過去の処理」を同じ概念で扱うため。
ファイルパス引数 --file, --to, --output でローカルパスを渡す。 変更 importId, downloadUrl, 管理ダウンロード先。 ブラウザ UI から任意ローカルパスを書かせる設計は危険で、説明もしづらいため。
ページング --page, --page-size が複数 CLI で既存。 維持 page, pageSize, totalCount 大量ファイル・大量会話で必須。既存契約とも相性がよい。
削除 dry-run items remove --dry-run, cleanup dry-run。 維持 dryRun, deletePlan 削除されるもの/残るものを確認してから実行するため。
元データ削除 各READMEで元ファイル、元ZIP、Codex履歴を削除しない方針。 維持 このAPI設計には含めない。 破壊的であり、生成物削除とは責務が違うため。
診断用コマンド Video の probe, sample, ocr, audio analyze など。 維持 通常 UI API には出さず、必要時だけ /diagnostics として予約。 通常ユーザー操作と開発/運用診断を混ぜるとUIが複雑になるため。
製品能力の推測 Timeline 側のコードが製品ごとの差分を知っている。 変更 /capabilities と timeline-product.json を正本にする。 後続製品を追加しても UI と API クライアントが推測を増やさずに済むため。

2. 全製品共通 API

ここは全サブ製品が同じ意味で持つ API です。現行 CLI の個別コマンドを、一般ユーザーに見える操作名へ寄せます。

2.1 状態確認
GET /{product}/health 全製品へ追加

API プロセス、常駐 worker、最低限の依存が生きているかを返します。Docker healthcheck や監視用の軽い確認です。

現行対応
各製品のローカル API が /health を提供する。
現行使用箇所
Docker healthcheck は Image / Video の worker Dockerfile。Timeline 本体は現状 /products/runtime/status や overview で代替確認しています。
変更点
CLI 実行の成否ではなく、HTTP 200 と短い JSON で稼働状態を返します。
主な返却
ok, state, productId, version, checks[]
理由
起動しているかどうかを、人間用の詳細表示や重い検査と分離するためです。
GET /{product}/status 既存 overview を統一

画面に表示する状態です。設定済みか、入力元が読めるか、出力先に書けるか、最後の処理が成功したか、次に何をすべきかを返します。

現行対応
settings status, doctor, 各製品の /products/{id}/overview。
現行使用箇所
Timeline の各一覧ページ、設定画面、ダッシュボードが overview を参照しています。
変更点
製品別の overview 名を /status に統一し、ユーザー向け表示に必要な状態を共通フィールドに寄せます。
主な返却
displayState, nextAction, settingsReady, inputReady, outputReady, latestTask
理由
「製品が使えるか」を製品ごとの実装差ではなく、同じ画面部品で判断できるようにするためです。
2.2 設定
GET /{product}/settings 既存

現在の設定を取得します。設定ファイルの場所、入力元、保存先、AI処理方法、トークン設定済みかどうかを返します。

現行対応
settings status, settings master show, settings output show。
現行使用箇所
Timeline 設定画面、各製品設定ページ、初期設定案内。
変更点
Audio の master、ChatGPT の output、WindowsCodex の master を outputRoot として揃えます。
理由
同じ「生成データの保存先」を製品ごとに別名で扱うと、Swagger と UI の理解コストが上がるためです。
PUT /{product}/settings 既存コマンドを統合

設定を保存します。入力元、保存先、処理方法、トークンなどを一つの設定更新として扱います。

現行対応
settings save, settings inputs add/remove/clear, settings master set, settings output set。
パラメータ変更
--input-root の繰り返しは inputRoots: []、--output-root / --to 系は outputRoot、--compute-mode は computeMode にします。
理由
Web UI では「現在の設定全体」を保存する操作になるため、CLI の追加・削除コマンド列より、設定オブジェクト更新の方が安全に差分確認できます。
POST /{product}/settings/check 追加

保存前または実行前に、設定が有効かだけを確認します。ファイルや会話の取り込みは行いません。

現行対応
doctor, config-check, settings status の検査部分。
変更点
検査結果を checks[] と blockingProblems[] に分けます。
理由
ユーザーに「何を直せば使えるか」を先に出すためです。処理開始後に失敗するより判断しやすくなります。
2.3 更新と処理
POST /{product}/refresh items refresh を統一

元データを確認し、新規または変更されたものを記録へ変換します。長い処理は即時完了ではなく処理IDを返します。

現行対応
items refresh、PC では capture と items refresh の意味を整理して対応。
現行使用箇所
Timeline の各製品ページの「更新」「再スキャン」「取り込み」ボタン、Timeline ストア再構築前の製品収集。
パラメータ変更
--max-items は limit、--item-id は recordIds、ChatGPT の --file は importId に分離します。
理由
製品差分を URL 名に出さず、更新という共通操作として扱うためです。進捗は /tasks/{taskId} に分けます。
GET /{product}/tasks 追加

進行中または最近の処理を一覧します。Web UI の進捗表示と操作ログの入口です。

現行対応
runs list、Timeline helper の operation logs、各製品の status.json。
理由
「処理中」「完了」「失敗」を CLI 標準出力から読み取るのではなく、API として確認できるようにします。
GET /{product}/tasks/{taskId} 追加

一つの処理の進捗、現在の段階、完了結果、失敗理由を返します。

現行対応
runs show --run-id、各 run/status ファイル。
主な返却
state, progressPercent, currentStage, message, result
POST /{product}/tasks/{taskId}/cancel 追加候補

長時間処理のキャンセルです。初期実装では「受け付け不可」を返してもよいですが、URL は予約します。

現行対応
明確な CLI 対応なし。現状は停止スクリプトやプロセス終了に寄りがちです。
理由
API 化すると複数アクセスと長時間処理が見えるため、キャンセル可否を契約として返す必要があります。
2.4 記録と出力
GET /{product}/records items list を改名

生成済みの記録を一覧します。内部の item は、ユーザー向けには record と呼びます。

現行対応
items list --page --page-size --json
現行使用箇所
Audio / Image / Video / PC の一覧、ChatGPT / WindowsCodex の会話一覧、Timeline ストア再構築。
パラメータ変更
page と pageSize は維持。製品固有の絞り込みは filter または製品別枝に置きます。
理由
Swagger 上で全製品の一覧操作を同じ型にするためです。
GET /{product}/records/{recordId} 整理して追加

一つの記録の詳細、タイムライン、生成物の参照を返します。

現行対応
製品ごとの detail API、生成済み timeline.json / convert_info.json の読み取り。
理由
詳細画面が、元ファイル詳細・会話詳細・PC記録詳細に分かれても、記録としての基礎情報は共通にできます。
POST /{product}/records/download items download を改名

選択した記録、または全記録の ZIP を作成します。実ファイルのダウンロード URL は別に返します。

現行対応
items download, items download --item-id, items download --to, --overwrite
パラメータ変更
--item-id は recordIds: []、--to は API 内部の管理ダウンロード先へ移し、画面側は返却された downloadUrl を使います。
理由
ブラウザ保存とサーバー側 ZIP 作成を分け、任意のローカルパスを書き換えないようにするためです。
DELETE /{product}/records/generated delete-generated/remove を統一

元データは残し、生成済みデータだけを削除します。

現行対応
Audio files/delete-generated、Image / ChatGPT / WindowsCodex の items/delete-generated、Video の items remove。
パラメータ変更
itemIds / sourceIds を recordIds に寄せます。dryRun は残します。
理由
削除対象が「元データではなく生成物だけ」であることを API 名から明確にするためです。

3. 製品グループ別 API

製品差分はここに閉じ込めます。全製品に専用 API を増やすのではなく、元データの種類ごとに枝を足します。

3.1 ファイル系: Audio / Image / Video
GET /{product}/sources settings inputs を整理

ユーザーが指定した入力フォルダーや入力ファイルを一覧します。

現行対応
Audio settings inputs list、Image / Video settings status 内の inputRoots。
理由
「元データの場所」と「処理済み記録」を分けることで、設定画面と一覧画面を整理できます。
PUT /{product}/sources add/remove をまとめる

入力元の一覧を保存します。追加・削除の個別コマンドではなく、現在の一覧を正として更新します。

現行対応
settings inputs add/remove/clear、settings save --input-root
パラメータ変更
inputRoots: [{ path, displayName, enabled }] に統一します。
理由
Web UI の保存前確認で「追加されるもの / 外れるもの」を表示しやすくするためです。
GET /{product}/files 既存

入力元にあるファイルを一覧します。まだ処理されていないファイルも含みます。

現行対応
files list --page --page-size --json
現行使用箇所
Audio の音声ファイル一覧、Image の画像一覧、Video の動画一覧。
変更点
URL は製品ごとに同じ。返却には recordState を入れ、未処理 / 処理済み / 変更ありを表します。
GET /{product}/files/{fileId} detail を整理

一つの元ファイルの詳細です。元ファイルの情報、対応する記録、生成物の有無を返します。

現行対応
Timeline helper の files/detail 系 API、Audio の詳細ページ、Image / Video の詳細ページ。
GET /{product}/files/{fileId}/source 既存

ブラウザで再生・表示するため、元ファイルを読み取り専用で返します。

現行対応
Timeline helper の files/source 系。Audio 再生、Image プレビュー、Video プレビューで使用。
責務
元ファイルを削除・変更しない。Range リクエスト、Content-Type、アクセス可能なルート制限を持つ。
3.2 会話系: ChatGPT / WindowsCodex
GET /{product}/conversations threads/items を改名

会話の一覧です。ChatGPT と WindowsCodex は、同じ会話系 UI として扱います。

現行対応
items list --json、Timeline helper の /products/{id}/items。
現行使用箇所
ChatGPT スレッド一覧、WindowsCodex スレッド一覧。
パラメータ変更
page / pageSize は維持。表示語は threads から conversations へ寄せます。
理由

5. 長時間処理の扱い

API 化で一番重要なのは、時間がかかる処理を通常の同期 API として扱わないことです。 Web UI から見ると、更新、ZIP 作成、削除、PC 記録、ChatGPT ZIP 取り込みは「押したらすぐ終わるボタン」ではなく、進捗を持つ処理として扱うべきです。

短い API

/health、軽い /settings、キャッシュ済み /status は数秒以内に返します。画面の定期確認に使えます。

重くなり得る API

/files、/records、/status の詳細検査は、件数や初回キャッシュで遅くなる可能性があります。ページングとキャッシュが必要です。

長時間 API

/refresh、/records/download、/records/generated、/pc/captures、/chatgpt/imports は処理IDを返して非同期にします。

5.1 長時間 API の基本形
POST /{product}/refresh 同期完了から処理開始へ変更

更新処理を開始し、完了を待たずに taskId を返します。HTTP レスポンスは 202 Accepted を基本にします。

現行の問題
CLI 実行中は呼び出し元が待ち続けます。動画、音声、ChatGPT ZIP、PC記録では数十秒から数十分になり得ます。
あるべき挙動
API は「処理を受け付けた」ことだけを返し、進捗は GET /{product}/tasks/{taskId} で確認します。
返却例
{ taskId, state: "queued", statusUrl, cancelUrl }
理由
ブラウザ、プロキシ、HTTP クライアントのタイムアウトに処理寿命を依存させないためです。
GET /{product}/tasks/{taskId} 進捗確認

現在の段階、進捗率、処理件数、現在処理中の対象、失敗理由、次の推奨操作を返します。

状態
queued, preparing, running, waiting, completed, failed, cancelRequested, cancelled, interrupted
途中経過
progressPercent, currentStage, itemsDone, itemsTotal, currentItemLabel, updatedAt
画面側
開始直後に処理カードを表示し、2〜5秒間隔で polling します。完了後は該当一覧を再読み込みします。
GET /{product}/tasks/{taskId}/events 任意追加

必要なら Server-Sent Events で進捗イベントを流します。初期実装は polling だけで十分です。

採用判断
まずは GET /tasks/{taskId} の polling を標準にします。SSE は動画や音声の細かい進捗が必要になった時だけ追加します。
理由
最初から WebSocket/SSE を必須にすると実装と復旧が複雑になります。状態ファイル/DB に進捗を残す polling の方が堅いです。
5.2 API ごとの同期/非同期判断
API 想定時間 推奨 理由
GET /{product}/health 1秒以内 同期 監視用です。重い検査、モデル確認、全件スキャンを含めません。
GET /{product}/status 通常 1〜3秒 同期 + キャッシュ 画面表示に必要ですが、詳細検査で遅くなる場合は前回結果と stale 表示を返します。
GET /{product}/files 件数次第 同期 + ページング + キャッシュ 動画や大量画像は初回が遅いです。refresh=true などで明示更新にします。
POST /{product}/refresh 長い 非同期 音声モデル、動画処理、ZIP展開、PC収集は長時間化します。taskId を返すべきです。
POST /{product}/records/download 中〜長 非同期 ZIP 作成は件数と容量に依存します。完了後に downloadUrl を返します。
DELETE /{product}/records/generated 中〜長 非同期候補 件数が少なければ同期でもよいですが、統一して task 化すると削除中表示と dry-run が扱いやすいです。
POST /pc/captures 中〜長 非同期 CIM/WMI、アプリ一覧、ディスク情報などで時間が変動します。進捗段階を出すべきです。
POST /chatgpt/imports ファイル次第 登録は同期、解析は非同期 ZIP の受け取り/登録と、会話変換処理は分けます。大きい ZIP は処理だけ task 化します。
5.3 複数アクセスとキュー

基本ルール

重い処理は、製品ごとに原則 1 本だけ同時実行します。読み取り API は動かしてよいですが、同じ生成データを書き換える処理はキューまたは拒否にします。

同時実行可
/health, /status, /records, /files, /tasks/{taskId}
同時実行制限
/refresh, /records/download, /records/generated, /pc/captures
重複リクエスト
同じ条件の処理が実行中なら、新しい処理を作らず既存の taskId を返す選択肢を持ちます。
理由
同じ outputRoot に複数処理が同時書き込みすると、成果物、latest ZIP、status.json が壊れる可能性があるためです。

Idempotency-Key

Web UI からの二重クリックや通信リトライに備えて、長時間 POST は Idempotency-Key を受け付けます。

あるべき挙動
同じ key と同じ本文なら同じ taskId を返します。違う本文なら 409 Conflict を返します。
理由
ユーザーがボタンを連打しても、同じ処理が複数走らないようにするためです。

排他ロック

API 層だけでなく、worker 側にもファイルロックまたは DB ロックを置きます。

必要な場所
outputRoot、latest ZIP、settings 書き込み、run/task 状態更新、Docker compose 起動。
理由
API サーバーが再起動しても、worker 側で成果物保護が効くようにするためです。
5.4 キャンセル、失敗、復旧

キャンセル

キャンセルは即時 kill ではなく、cancelRequested を保存し、worker が安全な区切りで停止します。

返却
canCancel, cancelRequested, cancelReason
できない場合
外部コマンドやモデル処理中で安全に止められない場合は canCancel: false を返します。
理由
生成途中のファイルやロックを壊さず、次回 refresh で復帰できる状態を保つためです。

失敗

失敗は「ユーザーが次に何をすべきか」を返す形にします。

返却
userMessage, technicalMessage, retryable, nextAction, logsUrl
理由
CLI の stderr をそのまま見せると、一般ユーザーが安全に判断できないためです。

復旧

API または worker が落ちた場合、次回起動時に古い running を interrupted にします。

必要な実装
task 状態の永続化、heartbeat 時刻、stale 判定、途中ファイルの cleanup または再利用判定。
理由
画面に「処理中」のまま残り続ける状態を避け、再実行できるかを明示するためです。
5.5 製品別の進捗ステージ案

5.6 運用上あるべき実装

操作ログ

全 task に operationId を持たせ、親 UI 操作、API リクエスト、worker 実行、旧 CLI 呼び出しをつなぎます。

安全なログ表示

トークン、パスワード、APIキー、個人情報になり得る値はログ保存前にマスクします。画面には短い説明を優先します。

キャッシュ

重い一覧や status は cachedAt と stale を返します。ユーザーが明示更新した時だけ再スキャンします。

タイムアウト

HTTP リクエストは短く、worker 処理は task として継続します。API タイムアウトと処理タイムアウトを混同しません。

古い処理の扱い

heartbeat が一定時間更新されない task は interrupted にします。次回 refresh で再開または再処理します。

互換期間

移行中は API 内部から現行 CLI を呼んでもよいですが、外部契約は API の task/records/status へ寄せます。

6. あるべき配慮

「必要最低限」ではなく「あるべきものがある」状態にするための採否です。 ただし、初期 API を重くしすぎないよう、入れるもの、予約だけするもの、今は入れないものを分けます。

必ず入れる

ヘルス、状態、進捗、データ鮮度、ユーザー向けエラー、元データ保護、部分失敗、製品能力 discovery。

予約する

SSE、診断 API、maintenance cleanup、詳細な認証、外部監視連携。URL と概念だけ先に置き、実装は後回しにします。

入れない

元データ削除、任意ローカルパスへの書き込み、複雑なユーザー管理、GraphQL、全製品共通の巨大ワークフローエンジン。

6.1 共通レスポンスに入れる配慮
配慮 共通フィールド 対象 API 理由
契約バージョン contractVersion, schemaVersion 全 API Swagger と実装のずれを検出しやすくするため。破壊的変更時の判断材料になります。
データ鮮度 dataFreshness.cachedAt, isStale, refreshAvailable /status, /files, /records, /conversations 重い一覧を毎回スキャンせず、UI が「この情報は古い可能性があります」と説明できるようにします。
ユーザー向けエラー errorCode, userMessage, technicalMessage, nextAction 全 API CLI stderr や Python 例外をそのまま表示しないため。一般ユーザーが次の行動を選べます。
部分失敗 partial, warnings[], failedItems[] /refresh, /records/download, /imports 大量ファイルや大量会話では、一部失敗でも成果物が有効なケースがあるためです。
元データ保護 sourceSafety.readOnly, sourceIncludedInExport, deleteSourceData /files, /records/download, 削除 API 各製品の README が持つ「元データを消さない、ZIPに含めない」方針を API 契約に出します。
伏字化 redaction.redacted, redactionProfile, containsSensitiveData PC、会話系、ログ表示、エラー表示 TimelineForPC の llm_safe と、会話履歴/ログ表示の安全性を同じ考え方で扱うためです。
出所と再処理判断 provenance.sourceFingerprint, settingsHash, modelVersions, sourceModifiedAt /records, /records/{id} 変更検出、再処理、スキップ理由、成果物の信頼性を説明するためです。
操作追跡 operationId, taskId, logsUrl 長時間処理、設定保存、削除、ダウンロード UI操作、API、worker、旧CLI呼び出しを一本の履歴として追えるようにするためです。
6.2 ユーザーに見せる言葉
内部語 API語 画面表示 使い分け
item record 記録 既存ファイル名やIDでは item を残してよいが、API正面は record。
run task 処理 現在実行中、待機中、失敗、完了をまとめて扱う。
inputRoot source 元データ ファイル系では入力フォルダー、ChatGPT ではインポートZIP、WindowsCodex では履歴ルート。
thread conversation 会話 ChatGPT / WindowsCodex の共通UIでは conversation を使う。
master / output outputRoot 保存先 製品ごとの差分名を API では統一する。
doctor settings/check または status 利用前チェック 軽いヘルスとは分け、ユーザーが直すべき問題を返す。
6.3 削除・上書き・ダウンロードの安全設計

削除

削除 API は生成物だけを対象にします。元ファイル、ChatGPT の元 ZIP、Codex の元履歴、PC の実体情報は対象外です。

必須
dryRun, deletePlan, willDelete[], willKeep[], requiresConfirmation
理由
既存ドキュメントでは、元データを削除しない方針が繰り返し示されています。API でもこの境界を崩しません。

上書き

ダウンロードやエクスポートは、API 管理下の保存先に作り、ブラウザには downloadUrl を返します。

変える点
CLI の --to, --output, --overwrite は、Web API の正面引数から外します。
理由
Web UI から任意の Windows パスを書き換える操作は、ユーザー説明と安全確認が難しいためです。

ダウンロード

ZIP 作成とファイル取得は分けます。ZIP 作成は task、ファイル取得は読み取り専用の download URL です。

返却
downloadUrl, fileName, sizeBytes, sha256, expiresAt
理由
大きい ZIP、途中失敗、再取得、ブラウザ保存を安定して扱うためです。
6.4 予約するが初期実装しないもの
機能 予約する形 初期実装しない理由 追加判断
リアルタイム進捗 /tasks/{taskId}/events polling で十分始められる。SSE/WebSocket は復旧と接続管理が増える。 動画・音声で細かい進捗が必要になったら追加。
診断 API /{product}/diagnostics/* 通常ユーザーの操作導線を複雑にする。 管理画面や開発者モードが必要になったら追加。
maintenance cleanup /{product}/maintenance/cleanup-plan 削除対象の説明と確認 UI が必要で、refresh より危険度が高い。 容量管理画面を作る段階で追加。
強い認証 ローカル token / allowlist 現段階ではローカル API 前提。多ユーザー権限は過剰。 LAN公開や外部連携が必要になった時だけ設計。
外部監視連携 /health のみ先に対応 OpenTelemetry などを最初から入れると運用前提が重くなる。 長期常駐運用や複数端末監視が必要になったら追加。
