# Dockerを外したいが、外しきるべきか悩んでいる

作成日: 2026-06-04

## 目的

Timeline を商品として扱う場合、Docker 必須は導入障壁になる。

一方で、Docker には明確な利点もある。

この資料では、現時点の悩みを決定事項としてではなく、検討中の意見として残す。

## 悩みの中心

単純に言うと、次の2つが衝突している。

```text
Dockerを外したい
  -> ユーザー導入を軽くしたい
  -> 起動や設定をわかりやすくしたい
  -> 商品として見せやすくしたい

Dockerを残したい
  -> 内部環境を汚したくない
  -> Python / AI / GPU / OCR / FFmpeg などの依存を隔離したい
  -> ユーザーPCに直接いろいろ入れたくない
```

つまり、本当に解きたい問題は「Dockerを消すこと」ではない。

本質的には、次の両立である。

> ユーザーには軽く見せたいが、内部実行環境は汚したくない。

## Dockerの旨味

### 依存関係を閉じ込められる

Timeline のサブ製品は、音声認識、話者分離、OCR、動画解析、LLM、FFmpeg などを扱う。

これらをユーザーPCに直接入れると、環境が汚れやすい。

Docker があると、依存関係をコンテナ内に閉じ込められる。

### 再現性が高い

同じイメージで動くため、開発環境と利用環境の差分を抑えやすい。

特に Python、PyTorch、CUDA、Tesseract、FFmpeg 周辺は、ローカル実行にすると差分が出やすい。

### アンインストールしやすい

コンテナ、イメージ、ボリューム、ネットワークを把握できれば、生成物を分けて消しやすい。

ユーザーのPC本体に何を入れたかが散らばりにくい。

### 重い処理を隔離できる

AI系の処理はメモリ、GPU、CPUを強く使う。

Dockerに閉じ込めることで、少なくとも実行単位として分離しやすい。

停止、再起動、ログ確認もしやすい。

## Dockerの弱点

### 商品として重く見える

一般ユーザーにとって、Docker はそれだけで導入障壁になる。

「Dockerを入れてください」と言った瞬間に、対象ユーザーがかなり絞られる。

開発者向けの初期ベータなら許容できるが、一般販売では重い。

### 起動が複雑になる

コンテナ、ネットワーク、ポート、ボリューム、イメージ、プロジェクト名など、管理対象が多い。

Timeline は複数サブ製品を扱うため、この複雑さが積み上がりやすい。

### 状態が見えにくい

ユーザーから見ると、何が起動していて、何が止まっていて、どこで処理が詰まっているのかがわかりづらい。

Docker Desktopを見ればわかるが、それを前提にする時点で商品としては弱い。

### PC負荷が大きく見える

Docker Desktop、複数コンテナ、AI処理が重なると、ユーザーには「重いアプリ」に見える。

実際の処理が重いだけでなく、心理的にも重く感じられる。

## 今の仮説

現時点では、いきなり Docker を完全撤去するのは危険。

より安全なのは、次の考え方である。

```text
Dockerを外す
  ではなく
Dockerをユーザーに意識させない方向へ寄せる
```

または、次のように段階を分ける。

```text
軽い処理
  -> native 実行へ移す

重いAI処理
  -> 当面は Docker も許容する

商品UI
  -> Dockerという言葉をできるだけ前面に出さない

内部設計
  -> docker / native を Runtime として抽象化する
```

## 実行方式の分離

Timeline から見ると、サブ製品が Docker で動いているか native で動いているかは、本来は重要ではない。

Timeline が知りたいのは次だけでよい。

- 起動できるか
- 停止できるか
- ヘルスチェックできるか
- ジョブを開始できるか
- ジョブを停止できるか
- 結果を取得できるか

そのため、理想的には次のように扱う。

```text
Timeline
  -> Product API
    -> Runtime
      -> Docker Runtime
      -> Native Runtime
```

この形にできれば、将来的に Docker を外すか残すかを製品ごとに判断できる。

## 商品化目線での暫定方針

初期検証では、Docker が残っていてもよい。

ただし、売り方としては次のように整理する。

```text
初期検証
  Dockerありでもよい
  対象は開発者・AI利用者に寄せる

有料ベータ
  Timeline本体はDockerなしを目指す
  重いAI系だけDockerを許容する

一般販売
  Dockerを意識しない起動方法を目指す
```

## 現時点で避けたいこと

- Docker撤去を急ぎすぎて、AI処理が不安定になる
- ユーザーPCにPython依存を直接ばらまく
- Dockerを消した結果、アンインストールや復旧が難しくなる
- 実行方式の違いがUIやTimeline本体に漏れすぎる
- 「Dockerなし」を売り文句にした結果、内部品質が落ちる

## 現時点の意見

Dockerは邪魔でもあるが、かなり重要な防波堤でもある。

特に Audio / Video / Image のような重いAI・変換系処理では、Dockerを外すほどユーザー環境に責任を持つ必要が出る。

そのため、現時点での意見は次の通り。

> Dockerを完全に外すことを目的にしない。
> まず、Dockerを使っていることをユーザーに感じさせない設計に寄せる。
> その上で、軽い処理から native 化し、重いAI系は最後に判断する。

## 未決定事項

- Timeline本体はいつ native 実行を標準にするか
- Audio / Video のAI処理を native 化するか
- Ollama を同梱・外部利用・Docker利用のどれにするか
- モデルキャッシュをどこに置くか
- GPU利用をどう扱うか
- Dockerあり版とDockerなし版を両方サポートする期間
- 商品ページで Docker の存在をどこまで説明するか

## 次に考えること

次に検討するなら、実装ではなく次の整理から始める。

- 製品ごとの Docker 依存一覧
- 製品ごとの native 化難易度
- Dockerを外すことで汚れる可能性がある場所
- Runtime 抽象化の仕様
- Docker版と native 版の比較テスト
- 商品としての導入説明

この資料は、Dockerを外す決定ではなく、外したい気持ちと残したい理由を忘れないためのメモである。
