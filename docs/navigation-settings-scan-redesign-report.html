Timeline 画面構造再設計レポート

設定、製品管理、スキャン、時間軸、分析、ログの役割を整理し、 Timeline 本体が「サブ製品の寄せ集め」ではなく「時間軸を扱う製品」として見えるようにするための設計レポート。

作成日: 2026-05-08 / 対象: Timeline Web UI / 状態: 段階実装中

実装済み

  • サイドバー上部の設定を外し、左下の補助導線へ移動した。
  • 操作ログページ、右下コンソール、ローカル実行表示を通常ユーザー向けUIから削除した。
  • 設定はページではなくモーダルとして表示する構成に寄せた。
  • 設定モーダル右上に固定の閉じるボタンを追加し、縦幅を抑えた。
  • 保存ボタンを1つに整理し、保存前に変更差分を確認するステップを追加した。
  • 未保存の設定がある状態で閉じる場合は、破棄確認を表示する。
  • 左下の補助導線に製品管理を追加し、製品の存在、配置、状態を読み取り専用で確認できるモーダルを追加した。

要約

現在の UI は、サブ製品が増えたことで「各製品の一覧ページ」と「各製品の設定」がサイドバーに広がり始めている。 初期段階では正しいが、Timeline 本体の価値が見えにくくなる。

次の段階では、サイドバーの主導線を ダッシュボード、スキャン、時間軸、分析、レポート に絞り、 設定と製品管理だけを左下の補助領域へ退避するのがよい。 ローカル実行とコンソールはユーザー向けUIから削除し、状態やログは内部で保持する。

今回の論点

設定が主機能に見える

設定は日常的に使うページではない。現在のサイドバー上では通常ページと同列に見えるため、 ユーザーの視線を主作業から外してしまう。

製品別メニューが増えすぎる

Audio、WindowsCodex、ChatGPT、Image に続き Video、PC、Web などが増えると、 サブ製品名と一覧ページだけでナビゲーションが膨らむ。

ログの入口が重複している

操作ログページとコンソールが並存している。通常ユーザーに見せる価値は低く、 インシデント対応用に内部ログとして保持する方がよい。

時間軸の前処理が見えにくい

スキャンで素材を取得し、時間軸で整理し、分析や記事生成に使うという段階が、 画面構造としてまだ十分に分離されていない。

ユーザーの心理モデル

この製品を使うユーザーは、サブ製品名や CLI の都合を知りたいわけではない。 期待しているのは、手元の素材が取り込まれ、時間軸に並び、分析や出力に使える状態になること。

ユーザーの問い 画面上の受け皿 隠したい内部概念
素材はちゃんと見つかっているか スキャン 製品別 CLI、items list、files list、worker 出力
変換できているか、失敗していないか スキャン詳細、進捗、警告 run、artifact、generated、source identity
いつ何があったか 時間軸 サブ製品ごとの JSON 形式差、タイムゾーン補正
LLM に渡せる読みやすい形になっているか 時間軸の整理、言語化状態 phone token、OCR raw、intermediate chunk
何を分析できるか 分析、レポート、記事生成 ストア構造、内部インデックス、ジョブ管理
問題が起きた時に原因を追えるか 通常UIには出さない。内部ログ、診断パック、インシデントレポートで扱う。 CLI標準出力、PowerShellログ、operation log、worker log

推奨する全体構造

サイドバーは「毎日使う作業」を中心にする。設定や製品管理は重要だが、日常操作ではないため左下の補助領域へ移す。 ローカル実行は製品前提そのものなので表示しない。コンソールもユーザー向けの常設UIから削除する。

配置方針

  • 上部: Timeline 本体の主作業だけを置く。
  • 中段: サブ製品名を常時展開しない。必要ならスキャン画面内のフィルタやタブで扱う。
  • 左下: 設定と製品管理だけを置く。
  • 表示しない: ローカル実行、コンソール、操作ログは通常ユーザー向けUIから外す。

これにより、サブ製品が増えてもサイドバーの密度が増えにくい。 新製品追加時も「スキャンの対象が増える」と認識できる。

異常時の調査情報は内部ログとして残し、必要に応じて診断パックやインシデントレポートとして取り出す。 常時表示のコンソールは、ユーザー体験としては負担が大きい。

設定の再設計

設定は通常ページではなく、左下の補助メニューから開くモーダルとして扱う。 直接 URL は保守用に残してもよいが、通常導線はページ遷移にしない。

モーダルの見た目

通常モードとプロモードの制御

プロモードで個別設定を変更したあと通常モードに戻す場合、単なる表示切り替えとして扱うと値の不整合が起きる。 ここは「表示モード」ではなく「設定管理方式」の切り替えとして扱うべき。

状態 意味 保存時の扱い
通常モード Timeline が保存先、作業領域、製品別出力先を自動管理する。 共通設定を保存し、製品別の個別上書きは使わない。
プロモード 各製品や内部ディレクトリを個別に設定できる。 明示された個別設定を保存する。通常モードの自動展開とは分ける。
プロから通常へ戻す 個別設定の利用をやめ、自動管理へ戻る。 確認を出し、保存ボタンで確定する。閉じるだけなら破棄する。

保存ロジックの推奨

  1. モーダルを開いた時点で、設定のスナップショットを1つ読み込む。
  2. 通常モードとプロモードは同じ draft model を編集する。
  3. 表示上は通常モードで省略しても、内部では draft に差分を保持する。
  4. 保存ボタンは1つだけにする。
  5. 保存ボタンを押したら、変更差分を一覧表示する確認ステップを挟む。
  6. 差分確認で「確定」を押した時だけ保存する。
  7. 閉じる時に未保存差分があれば確認する。
  8. 保存成功後だけ実設定へ反映し、必要なら再起動が必要であることを表示する。

保存前確認で見せる差分

表示項目 例 目的
変更対象 TimelineForAudio / AI処理方法 どの設定を変えるのか分かる。
変更前 CPU 戻したい時に判断できる。
変更後 GPU 保存後の状態を事前確認できる。
影響 TimelineForAudio の再起動が必要 保存後に何が起きるか分かる。

再起動が必要な設定

設定によっては、保存だけでは反映されない。特に CPU/GPU 切り替え、ディレクトリのマウント、 Docker Compose の構成に関わる項目は、Timeline 本体またはサブ製品の再起動が必要になる。

設定例 再起動対象 UIでの扱い
AI処理方法 CPU / GPU 対象サブ製品 保存前確認に「再起動が必要」と表示し、確定後に再起動中ステータスを出す。
入力ディレクトリ、出力ディレクトリ 対象サブ製品、場合により Timeline helper 保存後に再スキャンが必要なことも合わせて表示する。
Timeline の保存先 Timeline 本体 保存先の移行、再起動、再読み込みの扱いを分けて表示する。

再起動の実行はサブ製品操作に当たるため、引き続き各製品の既存入口または cli.ps1 経由に限定する。 Timeline がサブ製品 Docker を直接操作する設計にはしない。

製品管理の位置づけ

製品管理は設定に近いが、同じものではない。 設定は「使い方を決める」機能で、製品管理は「使える製品を増やす、更新する、外す」機能。

区分 含める内容 通常ユーザーへの見せ方
設定 表示言語、タイムゾーン、保存先、入力ディレクトリ、AIトークン、処理方法 左下の設定からモーダルで開く。
製品管理 Audio、Image、ChatGPT、WindowsCodex、Video、PC などのインストール、更新、削除、配置確認 左下の製品管理から開く。設定とは入口を分ける。

将来的に Timeline 本体だけをインストールし、そこからサブ製品を追加していくなら、 製品管理はかなり重要になる。ただし、設定モーダルにすべて詰めると重くなるため、 左下の隣接メニューとして独立させるのがよい。

ログとコンソール

操作ログは重要だが、通常ユーザーに見せる画面としては不要。 コンソールも、ユーザーが喜ぶ情報ではないため、表からきれいに削除する。 ただし、インシデント対応に備えて内部ログは保持する。

現在の要素 整理方針 理由
操作ログページ 通常ナビから削除。必要なら開発者用または診断用URLに限定する。 ユーザーの主作業ではない。
コンソール ユーザー向けUIから削除。右下、左下、下部の表示領域も残さない。 ユーザーに見せても判断材料になりにくく、画面のノイズになる。
履歴ボタン 削除。 操作対象が曖昧で、現状の価値が低い。

内部ログとして保持する情報

  • ユーザー操作: どのボタンが押されたか。
  • 実行対象: どの製品、どの CLI、どの操作か。
  • operation id: 後からログを追える識別子。
  • 状態: 開始、実行中、成功、失敗、タイムアウト。
  • エラー: CLI の exit code、標準エラー、失敗したステージ。

インシデント対応は別途設計する。通常画面には出さず、必要な時に診断情報をまとめて取得できる形がよい。 画面上に空のコンソール領域や履歴ボタンを残さない。

スキャンへの統合

サブ製品ごとの一覧ページは、Timeline 本体の主機能ではなく「素材が正しく取り込めているか」を確認するための補助機能。 そのため、サイドバー上では スキャン に統合する。

現在 統合後 詳細の扱い
TimelineForAudio / ファイル一覧 スキャン / 音声 ファイルをクリックすると音声詳細モーダル。再生、区間、言語化状態を確認。
TimelineForImage / ファイル一覧 スキャン / 画像 画像プレビュー、OCR、解析結果をモーダルで確認。
TimelineForWindowsCodex / スレッド一覧 スキャン / Windows Codex スレッド本文はモーダルまたは詳細パネルで確認。
TimelineForChatGPT / スレッド一覧 スキャン / ChatGPT 取り込み済みスレッドの内容確認と処理状態を表示。

スキャン画面の役割

  • 素材が見つかっているか確認する。
  • 取り込み済み、未処理、失敗、警告を確認する。
  • 製品ごとの処理状況を同じ画面で比較する。
  • 必要な時だけ製品別の詳細を開く。
  • メインの分析画面とは分ける。

スキャンは「ローデータ取得」という意味合いに近いが、その言葉はユーザー向けには使わない。 画面名は スキャン、説明では 素材の取り込み状況 と表現するのが分かりやすい。

スキャンと時間軸整理を一緒にする案

本質的には、ユーザーはスキャン、変換、言語化、整理のボタンを押したいわけではない。 できるだけ自動で最新状態を保ち、必要な時だけ状態や詳細を確認できる画面が望ましい。

ABC比較用の試作HTMLを作成済み: スキャンと時間軸整理 UI 試作

案A: 取り込み状況ダッシュボード型

スキャン、変換、言語化、時間軸反映を1つの「取り込み状況」として見せる。 ユーザーは状態を見るだけで、通常は実行ボタンを押さない。

全体状態: 最新です / 処理中です / 対応が必要です
音声: 79件中79件 取り込み済み、75件 言語化済み
画像: 665件中665件 取り込み済み
ChatGPT: 3299件 取り込み済み
詳細は各行クリックでモーダル

最も分かりやすい。最初の実装候補。

案B: 時間軸を整える中心型

画面名を「時間軸」に寄せ、上部に「自動で整えています」という状態を出す。 スキャンは時間軸を作るための内部ステップとして吸収する。

時間軸の状態: 整理中 / 最新
次の処理: 音声の言語化、画像OCR反映
タイムライン一覧
未反映素材、警告、処理失敗は折りたたみ

Timeline 本体の価値は前に出るが、素材確認の入口が少し分かりにくくなる。

案C: 自動処理センター型

スキャン、変換、言語化、時間軸反映を「自動処理」としてまとめる。 処理待ち、処理中、失敗だけを見せる。

自動処理: 稼働中
待機中: 0件 / 処理中: 1件 / 未解決: 2件
最近の処理: 音声言語化、画像取り込み、ChatGPT反映
素材別詳細はフィルタで確認

実運用には強いが、初見ユーザーには「何を見ればいいか」が少し抽象的。

レビュー結果として 案C: 自動処理センター型 を採用する。 ここではスキャン、変換、言語化、時間軸反映をユーザーが毎回実行する操作ではなく、 Timeline が最新状態を保つための自動処理として扱う。 画面は価値提供そのものではなく、現在の状態、待機中、処理中、失敗、未解決を正確に伝える役割に寄せる。

時間軸と「整理」の役割

スキャンは素材を見つけて変換する段階。時間軸は、それらを時系列に並べ、分析や LLM へ渡しやすい形に整える段階。 ここには、単なる並べ替えだけでなく、音声の言語化や重複整理も含まれる。

スキャン 素材を見つける
変換 製品ごとに処理する
整理 時間軸に使える形へ整える
分析 意味や傾向を見る
出力 LLM用・記事・レポート

「最適化」の代替語

候補 評価 使いどころ
整理 最も分かりやすい。技術臭が少ない。 画面名、ボタン名、状態名に使える。
時間軸を整える 処理内容が伝わりやすい。 主要ボタン名に向く。
分析準備 目的は伝わるが、作業感が強い。 説明文や内部セクション名に向く。
最適化 意味は近いが一般ユーザーには硬い。 内部用語に留める。

推奨は、サイドバー名を 時間軸 のままにし、ページ内の主要操作を 時間軸を整える にすること。未言語化データの一括言語化も、この「整える」の一部として扱う。 ただし、理想はユーザーがそのボタンを頻繁に押さなくてよい状態で、常に自動で最新化されること。

分析と出力の位置づけ

Timeline のメイン価値は、スキャン済み素材を眺めることではなく、時間軸を使って分析、検索、記事化、レポート化できること。 そのため、将来的には 分析 と レポート を主導線に置く。

機能 役割 UIの置き場所
LLM用ダウンロード 整えた時間軸を外部またはローカルLLMへ渡せる形で出力する。 時間軸、分析、レポートのいずれかから実行。
ローカル分析 Ollama などを使ってローカルで分析する。 分析ページ。
記事生成 時間軸から記事、日報、記録、振り返りを生成する。 レポートまたは記事ページ。
期間指定出力 今日、今週、会議単位などで必要範囲だけを切り出す。 時間軸または分析ページ。
意味ベクトル検索 言葉が完全一致しなくても、意味が近い出来事、会話、画像、記事候補を探す。 分析、検索、記事生成の下地。

意味ベクトルは、Timeline の分析機能を強くする可能性が高い。 ただし、最初から画面に「ベクトル」という言葉を出す必要はない。 ユーザー向けには「似た内容を探す」「関連する出来事を集める」「記事の材料を探す」と表現する方がよい。

推奨する移行ステップ

  1. 実装済み: 設定モーダルの整理 サイドバー上の設定を左下へ移し、モーダル縦幅、保存ボタン、閉じる操作、通常/プロモードの保存制御を整理する。
  2. 実装済み: 操作ログページとコンソールを通常UIから削除する 内部ログは残すが、ユーザー向けの空間としては見せない。
  3. 実装済み: 製品管理の入口を左下に作る まずはインストールや更新を実行しなくてもよい。製品の存在、配置、状態を一覧できる入口にする。
  4. 実装中: スキャンと時間軸整理を自動処理センター型へ寄せる ABC案を比較し、案Cを採用した。まずは画面名とサイドバー導線をスキャンに寄せ、処理状態を中心に見せる。
  5. 既存の製品別一覧ページを隠す 直接URLは残してもよいが、サイドバーからは外す。
  6. 時間軸の整理機能を明確化する 「時間軸を再構築」よりも「時間軸を整える」に寄せる。ただし、最終的には自動実行を基本にする。
  7. 分析とレポートを主導線に育てる 最初はモックでもよいが、Timeline本体の価値がここにあることを画面構造で示す。

実装時の注意点

サブ製品操作は引き続き cli.ps1 経由にする。

スキャン統合後も、Timeline がサブ製品 Docker を直接触らないルールは変えない。

詳細モーダルは既存ページの完全コピーにしない。

スキャン詳細は「取れているか確認する」ための画面なので、編集や高度な分析は置かない。

設定と製品管理を混ぜすぎない。

製品管理は将来インストール、アンインストール、更新、ライセンスにも関わるため、設定とは別の入口がよい。

既存URLは急に壊さないが、通常導線からは外す。

過去の直接URLや検証用URLは残してよい。ただしサイドバーの主役にはしない。

ユーザーに見せないと決めたUIは、隙間も含めて削除する。

コンソール、操作ログ、ローカル実行は、非表示にするだけでなく通常UIの構成から外す。

自動処理を前提にする。

スキャン、変換、言語化、時間軸反映は、ユーザーが毎回押すものではなく、最新状態を維持する処理として設計する。

推奨結論

次のUI整理は、設定モーダルの細部修正だけでなく、サイドバー全体の意味を変える作業として扱うべき。 サブ製品ごとの一覧や設定を前面に出す段階は終わりつつある。

推奨する最終形は、主導線を ダッシュボード、スキャン、時間軸、分析、レポート に集約し、 左下には 製品管理、設定 だけを置く構成。 これなら、今後サブ製品が増えても Timeline 本体の価値が崩れにくい。

ローカル実行、操作ログ、コンソールはユーザー向けUIから削除する。 ログは内部保持し、インシデント対応時に取り出せる形を別途設計する。 スキャンと時間軸整理は、最終的には自動で最新状態を保つ方向へ寄せる。
