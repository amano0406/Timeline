# Timeline Jira運用ルール

このドキュメントは、Timeline の開発を Jira で管理するときの基本ルールをまとめる。

Timeline の Jira は、実装計画と進捗管理の正本として扱う。GitHub はコードの正本であり、Jira は「何を、なぜ、どこまでやるか」を管理する場所とする。

対象プロジェクト:

- Jiraサイト: `https://amanosystemlab.atlassian.net`
- Jiraプロジェクト: `KAN`
- Atlassian Rovo の `cloudId`: `https://amanosystemlab.atlassian.net`
- 一覧: https://amanosystemlab.atlassian.net/jira/software/projects/KAN/list?jql=project%20%3D%20KAN%20ORDER%20BY%20cf%5B10019%5D%20ASC

状態確認、完了判定、PBI の有無確認は、ローカル資料だけで判断しない。必要に応じてクラウド Jira を直接確認する。ローカルの受入レポート、作業メモ、スクリーンショット、動画、ログは補助証跡として扱う。

Jira 上で確認済みの主なチケット種別:

- `エピック`: 大きなユーザー価値やプロダクト状態を束ねる
- `ストーリー`: ユーザー価値を表す
- `Feature`: 機能まとまりを表す。使う場合はストーリーやタスクとの関係を明確にする
- `タスク`: 実装、調査、検証、運用整備を表す
- `バグ`: 期待状態と実際の状態のずれを表す
- `Subtask`: 親チケット内の分担や確認作業を表す

## 基本方針

Timeline のチケットは、単なる作業メモではなく、ユーザー価値、判断理由、完了条件を残すために使う。

特にAIエージェントに実装を依頼する場合、エピックだけを見て作業を完了扱いにしてはいけない。エピックは大きな目的を示す器であり、実際の作業はストーリー/PBI、タスク、不具合、必要に応じてサブタスクに分解して管理する。

ただし、未来の構想を最初から細かく分解しすぎない。PBIやタスクは、直近で実際に作業する範囲を中心に作る。将来の構想はエピック本文やコメントに留め、作業が近づいた時点で分解する。

## チケット階層

### エピック

エピックは、複数のストーリー/PBI、タスク、不具合を束ねる大きなテーマを表す。

例:

- CPUモードでTimeline全体を成立させる
- ランチャー化により起動・停止・復旧を整理する
- Mac環境でTimelineを利用できる成立性を作る
- インストール・アンインストール体験を整理する

エピックに書くべきこと:

- 背景
- 目的
- ユーザー価値
- スコープ
- 非スコープ
- 受入条件
- 想定する下位タスク

エピックの完了条件:

- 関連するストーリー/PBI、タスク、不具合が整理されている
- 必要な実装と検証が完了している
- 未対応事項が残っている場合は、別チケットとして分離されている
- エピックの目的がユーザー目線で満たされたと判断できる

エピックだけを作成した段階では、作業は完了していない。

### ストーリー / PBI

ストーリー/PBIは、ユーザーにとって意味のある価値単位を表す。

原則として、Who、What、Why を中心に書く。

例:

```text
ユーザーとして、
Timelineを起動したときに必要な処理環境の状態を確認したい。
なぜなら、スキャンできない原因が自分に分からないと、製品が壊れているように見えるから。
```

ストーリー/PBIに書くべきこと:

- 対象ユーザー
- そのユーザーが達成したいこと
- なぜそれが必要か
- 受入条件
- 検証方法

ストーリー/PBIでは、実装方法を主役にしない。How が主役になる場合は、タスクに落とす。

### タスク

タスクは、実装、調査、設計、検証、運用整備などの作業単位を表す。

タスクに書くべきこと:

- 何をするか
- なぜ必要か
- どう確認するか
- 関連するストーリー/PBIまたはエピック

タスクは開発者目線で書いてよいが、最終的にどのユーザー価値へ接続するかを見失わない。

### 不具合

不具合は、期待した状態と実際の状態がずれている場合に作る。

不具合に書くべきこと:

- 期待される動作
- 実際の動作
- 再現手順
- 影響範囲
- 原因の仮説
- 修正方針
- 再発防止または検証方法

不具合は、単に「直した」だけで閉じない。ユーザーが同じ問題に再遭遇しにくい状態になったかを確認する。

### サブタスク

サブタスクは、既にあるストーリー/PBIやタスクを細かく分ける必要があるときだけ使う。

サブタスクを増やしすぎると管理が重くなるため、以下の場合に限定する。

- 1つのチケット内で作業者や責務が明確に分かれる
- UI、API、検証などの完了確認を分けたい
- 途中状態を明確に追跡したい

## 2W1H

Timeline のチケットは、原則として 2W1H で書く。

- What: 何をするか
- Why: なぜ必要か
- How: どう実現・確認するか

ストーリー/PBIでは Why を強く書く。タスクでは How を明確に書く。エピックでは What と Why を中心にし、How は細かく書きすぎない。

## 受入条件

受入条件は、機能が存在するかではなく、ユーザーの目的が満たされたかを確認できる形で書く。

悪い例:

```text
ボタンが実装されている。
```

良い例:

```text
ユーザーが処理環境の異常を画面上で理解でき、復旧操作を迷わず開始できる。
```

Timeline では、画面やAPIができただけでは完了扱いにしない。素材が取り込まれ、時系列化され、必要に応じて概要やZIP出力を通じて AI が使える作業文脈になったかを重視する。

AI が関わるストーリー/PBIでは、単にAIが返答すること、画面に文言が出ること、APIが存在することだけを受入条件にしない。Timeline が持つ素材、概要、時系列イベント、出力ZIPが、ユーザーの次の判断やAI利用に役立つ状態になったかを確認する。

## 検証方法

検証方法はチケットごとに明記する。

主な検証種別:

- コードテスト
- 画面レビュー
- 実データ確認
- Docker / Local API の状態確認
- サブ製品連携確認
- AI利用確認
- ZIP出力確認
- ユーザー文言確認

これらを混同しない。たとえば、コードテストが通っていても、画面上でユーザーが理解できないなら、ユーザー体験としては未完了の可能性がある。

## 完了判定

エピックは、関連するストーリー/PBI、タスク、不具合が整理され、ユーザー価値が満たされたと判断できる場合に完了候補になる。

ストーリー/PBIは、受入条件を満たし、必要な証跡が残り、重大な不具合や未整理の追加作業が残っていない場合に完了候補になる。

タスクは、定義した作業が完了し、関連するストーリー/PBIまたはエピックに結果が反映されている場合に完了候補になる。

不具合は、再現手順で修正後の動作を確認し、同じ問題にユーザーが再遭遇しにくい状態になった場合に完了候補になる。

次の場合は完了扱いにしない。

- エピックだけが作られていて、ストーリー/PBIやタスクが未整理である
- 実装はあるが、ユーザー価値との接続を説明できない
- 受入条件が存在しない、または古い
- コードテストだけが通っていて、必要な画面確認、実データ確認、サブ製品連携確認が未実施である
- Timeline の目的である素材取り込み、時系列化、概要、ZIP出力、AI利用文脈のいずれかに影響する未整理事項が残っている
- 重大な不具合が別チケット化もコメント整理もされていない
- チケット本文やコメントから、何をもって完了としたか追えない

## エピックだけで実装依頼された場合

AIエージェントまたは開発者がエピックだけを見て実装を始める場合は、まず以下を確認する。

1. エピックの目的が明確か
2. ユーザー価値が明確か
3. ストーリー/PBIに分解できるか
4. 実装タスクに分けられるか
5. 検証方法が書けるか

分解できない場合は、いきなり実装せず、ストーリー/PBIまたはタスク案を作る。

エピックを直接「完了」にしない。完了判断は、下位チケットの完了、検証結果、残課題の分離を確認してから行う。

## 割り込み作業の扱い

ユーザーから割り込み作業、既存チケットにない作業、調査中に見つかった追加作業を依頼された場合は、対応前または対応後の切りのよい時点で Jira チケット化する。

ただし、すべての細かい修正を即時チケット化する必要はない。以下の場合はチケット化する。

- 作業が複数日にまたがる
- 後から経緯を追う必要がある
- ユーザー価値や仕様判断を含む
- 不具合の再発防止が必要
- 他のエピックと関係する
- 実装後に検証が必要

## コメント運用

チケットのコメントは、作業ログではなく、判断や状態を後から追えるようにするために使う。

コメントに残すべきこと:

- 方針変更
- 重要な判断
- 未解決のリスク
- 検証結果
- 失敗した原因
- 次に見るべき場所
- ユーザー確認が必要な点

コメントに残さなくてよいこと:

- 単なる途中経過
- ローカルだけの一時ログ
- すぐ消える検証メモ

## 完了時の扱い

チケットを完了する前に、以下を確認する。

- 説明が古くなっていないか
- 受入条件を満たしているか
- 検証方法と結果が分かるか
- 残課題が別チケット化されているか
- 関連するエピックの状態に反映すべきか

完了した作業は、チケットの状態、説明、コメントが古いままにならないよう更新する。

## JiraとGitHubの関係

Jira は計画、価値、進捗、判断の正本として扱う。

GitHub はコード、差分、レビュー、リリース履歴の正本として扱う。

Jiraにコードの詳細をすべて書く必要はない。GitHubにユーザー価値や完了条件をすべて閉じ込めてもいけない。

## 実装着手前チェック

実装に入る前に、次を確認する。

- 対応するエピックが明確か
- ユーザー価値を持つ作業ならストーリー/PBIがあるか
- 実装、検証、運用整備ならタスクとして切れているか
- 不具合なら期待動作、実際の動作、再現手順、影響範囲が書けるか
- 受入条件がユーザー価値に結びついているか
- 検証方法が明確か
- 画面、Local API、Docker、サブ製品、AI利用、ZIP出力のどれを確認すべきか分かっているか
- 関連する不具合や追加作業が放置されていないか
- 必要に応じてクラウド Jira 上の状態を確認したか

## 公開される可能性への配慮

このドキュメントは、公開されても困らない抽象度で書く。個人情報、秘密情報、認証情報、非公開の顧客情報は書かない。

一方で、Timeline の開発運用として正式に扱う。単なる一時メモではない。
