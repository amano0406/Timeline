Timeline LLM データルール

作成日: 2026-05-07 / 対象: Timeline 本体 / 版: v1 draft

目的

Timeline は、各サブ製品が作った時間軸データを保存し、あとから LLM で分析、検索、記事化、 レポート化できるようにする親製品である。この文書では、Timeline のマスターデータ、 LLM に渡す入力データ、LLM が生成した結果を混同しないためのルールを定義する。

基本方針は、マスターには正本と再検証に必要な情報を残し、LLM には読めるテキストを中心に渡すこと。 正しさは Timeline 側で保持し、LLM 入力では使えることを優先する。

3層モデル

層 目的 優先すること 例
Timeline マスター あとから検証、再生成、再解釈できる正本を保存する。 正しさ、出所、再現性。 元ファイル参照、phone token、OCR結果、生成経路、イベント時刻。
LLM 入力データ 分析やレポート生成のため、LLM が直接読める材料を作る。 読みやすさ、目的適合性、情報欠損を避けること。 言語化済み発話、会話本文、OCR済みテキスト、画像説明、スレッド要約。
LLM 生成結果 LLM が作った記事、分析、仮説、次アクションを保存する。 入力参照、生成日時、生成モデル、再生成可能性。 活動復元レポート、プロダクト棚卸し、感情ホットスポット分析。

Timeline における真実

Timeline の一次的な真実は、LLM がどう解釈したかではなく、いつ、どの出所から、 何が記録されたかである。

  • いつ発生したか。
  • 何を発したか。
  • 何を聞いたか。
  • 何の情報を受け取ったか。
  • 何をしたか。
  • 何に返信したか。
  • どのサブ製品、ファイル、成果物に由来するか。

LLM が生成した文章は、「LLM がその時その入力から生成した派生データ」という事実として保存する。 生成内容そのものを一次事実として扱わない。

直接読みにくいデータの扱い

レポート生成、記事生成、検索回答、自己分析などの通常の LLM 入力には、 直接読みにくいデータを渡さない。

データ Timeline マスター 通常の LLM 入力 理由
phone token 保存する 渡さない 人間にも LLM にも直接解釈しづらく、分析入力として無駄が大きい。
OCR 前の画像 参照を保存する 渡さない 画像解析を LLM 入力側に押し込むと重い。OCRや画像説明後のテキストを渡す。
動画フレーム 参照を保存する 渡さない 動画理解は前処理側で行い、シーン説明、OCR、音声言語化結果を渡す。
バイナリファイル 参照を保存する 渡さない LLM が一次情報として読めるテキストへ加工してから渡す。
例外として、音声言語化ジョブのような「読みにくい中間データを読めるテキストへ変換する専用処理」では、 phone token を内部入力として使うことがある。これは通常のレポート生成用 LLM 入力とは別の処理である。

サブ製品ごとの代表表現

各サブ製品の出力は、Timeline マスターでは詳細に保存し、LLM 入力では代表表現を優先する。 代表表現は「そのデータ種別を LLM が読むなら、まずこれを見る」という主テキストである。

製品/データ種別 LLM に渡す代表表現 補足として入れる情報 通常は入れない情報
TimelineForAudio 言語化済み発話、話者、発話時刻。 言語化経路、録音ファイル名、録音日時、前後文脈。 phone token 全文。
TimelineForChatGPT スレッドタイトル、user/assistant の会話本文、日時。 メッセージ数、更新日時、元スレッドID。 UI表示用だけの重複テキスト。
TimelineForWindowsCodex スレッドタイトル、依頼内容、応答内容、作業結果、変更概要。 作成日時、更新日時、変更ファイル、実行ログの要点。 大量の未加工ログ、重複した標準出力全文。
TimelineForImage OCR済みテキスト、画像説明、検出された対象、撮影/作成日時。 ファイル名、パス、画像サイズ、生成物の有無。 画像バイナリ、OCR前画像そのもの。
将来の TimelineForVideo 音声言語化、シーン説明、OCR済み画面テキスト、区間要約。 開始/終了時刻、動画ファイル名、シーン境界。 動画フレーム列、音声の中間トークン。
将来の文書/PDF/CSV 抽出テキスト、見出し、表の説明、重要列、集計。 ページ番号、シート名、行数、ファイル名。 未解析バイナリ、巨大な全行データ。

LLM 入力データ束

レポートや記事を作るときは、Timeline マスターをそのまま全件投入しない。 目的、期間、対象製品に応じて LLM 入力データ束を作る。 英語名としては Evidence Pack と呼べるが、UI 上では「分析用データ」や「レポート材料」と表示する。 

{
  "packId": "llm-input-pack-20260507-001",
  "purpose": "activity_report",
  "targetPeriod": {
    "from": "2026-05-01T00:00:00+09:00",
    "to": "2026-05-07T23:59:59+09:00"
  },
  "inputPolicy": {
    "textOnly": true,
    "excludeHardToReadIntermediateData": true,
    "securityRedaction": "minimal"
  },
  "items": [
    {
      "itemId": "audio-001-turns",
      "sourceProduct": "TimelineForAudio",
      "kind": "speech",
      "timeRange": {
        "from": "2026-05-04T10:21:00+09:00",
        "to": "2026-05-04T10:23:00+09:00"
      },
      "text": "Timelineのレポート生成について話している可能性が高い。",
      "note": "この文章は、TimelineForAudioのphone tokenをTimeline側で前後情報を使って言語化した候補です。",
      "sourceEventIds": ["audio-event-001"],
      "rawRefs": ["store/items.jsonl#audio-item-001"]
    }
  ]
}

生成経路の明示

言語化済み音声、OCR結果、画像説明、要約などは、どのような経路で作られたかを LLM に伝える。 個々の入力に長い注意書きを毎回重ねるのではなく、入力データ束の共通前提として宣言する。 

{
  "assumptions": [
    "TimelineForAudioの音声テキストは、元音声から直接の文字起こしではなく、phone tokenをTimeline側で前後情報を使って言語化した候補です。",
    "LLM生成結果は一次事実ではなく、Timelineマスターに基づく派生解釈です。",
    "直接読みにくい中間データは通常の分析入力から除外しています。必要な場合はrawRefsを参照してください。"
  ]
}

時間的ヒント

近い時間の別製品データは重要なヒントになる。ただし、何分、何時間、何日までを使うかは固定しない。 会議分析、日報、案件分析、感情分析、製品棚卸しで必要な範囲が異なるため、目的ごとに決める。

目的 初期候補 考え方
音声発話の言語化 前後 30 分から数時間 同じ作業中のチャット、Codex、ファイル名を弱いヒントにする。
日次活動復元 対象日全体 同じ日の作業、会話、音声、画像をまとめる。
プロダクト棚卸し 数週間から数か月 製品名やトピックで絞り、時間範囲は広めに取る。
案件/金銭判断 対象スレッドと関連資料中心 使えることより正確性を優先し、推測を分ける。

再生成ルール

  • LLM 入力データ束や LLM 生成結果は自動で無制限に再生成しない。
  • モデル変更、プロンプト変更、元データ変更があっても、原則はユーザー操作で再生成する。
  • 古い生成結果は消さず、生成日時、入力データ束ID、モデル名を残す。
  • 演算量が大きいため、バックグラウンドで勝手に再生成し続けない。

セキュリティと情報欠損

v1 では、外部 LLM とローカル LLM の厳密な分離や強い自動マスキングを主軸にしない。 過剰な削除により文脈が欠損するリスクが高いためである。

ただし将来のために、入力データには出所、製品、種類、raw 参照を残し、 後から情報分類やマスキングを追加できる形にする。

v1 共通フィールド

将来サブ製品が増えても、最低限このフィールドを持てば Timeline で扱える。 永遠に壊れない形式は狙わず、今のベストとして v1 を定義する。 

{
  "id": "string",
  "sourceProduct": "string",
  "kind": "string",
  "occurredAt": "ISO-8601 datetime",
  "timeRange": {
    "from": "ISO-8601 datetime",
    "to": "ISO-8601 datetime"
  },
  "title": "string",
  "text": "string",
  "notes": ["string"],
  "sourceEventIds": ["string"],
  "rawRefs": ["string"],
  "createdBy": {
    "type": "source_product | timeline | llm",
    "name": "string",
    "version": "string"
  }
}

プレビュー取得の扱い

画面で LLM 入力データ束を確認するときは、全件集計を前提にしない。 まずはページ表示に必要な件数だけを取得し、読みにくい中間データが続く場合は走査上限で止める。 これにより、Audio の phone token のような大量の中間データがあっても、画面操作を長時間ブロックしない。

Audio については、Timeline 側の言語化結果が存在する区間だけを LLM 入力候補にする。 言語化できていない phone token は、Timeline マスターには残すが、通常の分析用 LLM 入力からは除外する。

正確な総件数が必要な処理では、プレビューではなく専用の作成ジョブとして実行し、進捗とログを残す。

今後の実装順

  1. Timeline Store の items/events から LLM 入力データ束を作る内部モデルを追加する。
  2. Audio、ChatGPT、Windows Codex、Image の代表表現をマッピングする。
  3. Timeline 画面または Reports 画面で、対象期間と目的を選んで入力データ束を作れるようにする。
  4. 最初のレポートテンプレートとして、活動復元、プロダクト棚卸し、案件レーン分析を実装する。
  5. LLM 生成結果を Timeline Store の派生データとして保存する。
