Timeline サブ製品管理設計（旧案）

この資料はサブ製品管理を検討した初期メモです。現在の実装方針は settings-unification-design.html と settings-unification-todo.md を優先します。 製品をまとめる親ディレクトリ概念は採用せず、製品ごとの管理配置だけを扱います。

Timeline は親製品であり、TimelineForAudio、TimelineForWindowsCodex、 TimelineForChatGPT、TimelineForImage などのサブ製品を利用して時間軸データを構築する。 一般ユーザーが Timeline 本体だけを入れた場合、サブ製品が存在しない可能性が高いため、 サブ製品の場所、導入状態、更新、削除を Timeline 側で管理できる必要がある。

現段階の実装では、インストールや更新を自動実行しない。 まずは製品レジストリを導入し、固定パス依存を減らす。

目的

  • Timeline 本体が、各サブ製品の導入状態を把握できるようにする。
  • CLI 呼び出し先を固定パスではなく設定から解決する。
  • 開発環境の C:\apps 配置は維持する。
  • 一般ユーザー向けにも、製品ごとの管理配置を設定できるようにする。
  • 将来的に Release ZIP、Git clone、配信サーバー方式へ拡張できる形にする。

製品レジストリ

Timeline の settings.json に productRegistry を持たせる。 これは UI と Helper が参照するサブ製品管理の起点となる。 

{
  "productRegistry": {
    "products": [
      {
        "id": "audio",
        "displayName": "TimelineForAudio",
        "path": "C:\\apps\\TimelineForAudio",
        "sourceType": "release",
        "sourceUrl": "",
        "version": "",
        "enabled": true,
        "required": false
      }
    ]
  }
}

パス解決ルール

  1. path が存在すれば、それを使う。
  2. path が存在しない場合は、製品が見つからない状態として表示する。
  3. 旧形式の installPath や developmentPath は読み取り時の移行互換だけで扱う。

このルールにより、開発者の C:\apps 環境はそのまま動き、 一般ユーザー環境でも選択した製品配置から CLI を呼び出せる。

サブ製品マニフェスト

製品をインストールした後は、サブ製品ルート直下の timeline-product.json を読んで、起動、停止、CLI、設定ファイル、生成データ、アンインストール時の扱いを解決する。 Timeline 側は、製品ごとの Docker 名や生成データの場所を推測しない。

インストール前はサブ製品のファイルを読めないため、入手元と配置先は引き続き productRegistry で管理する。 インストール後の製品固有情報は timeline-product.json を正とする。

詳細仕様は docs/timeline-product-manifest.md にまとめる。

入手方式の比較

方式 用途 利点 弱点
local 開発・手動配置 既存環境に合わせやすい 一般ユーザーには配置判断が難しい
git 開発者・検証 更新と差分確認が容易 Git 導入やアカウント前提になりやすい
release 一般ユーザー初期配布 Git 不要で ZIP 展開だけで済む リリース作成と互換性管理が必要
managed-server 将来の収益化・配信管理 ライセンス、バージョン、配布制御を持ちやすい 配信サーバー運用が必要

Release ZIP の統一ルール

一般ユーザー向けのインストールは Git clone ではなく、GitHub Release の ZIP asset を優先する。 そのため、Timeline 本体と各サブ製品は同じ名前・同じ生成方法の配布 ZIP を持つ。 

scripts\build-release-bundle.ps1 -Version v0.2.0

生成物は次の形式に統一する。

release\v0.2.0\<RepositoryName>-windows-local.zip
release\v0.2.0\SHA256SUMS.txt

ZIP は Git タグから作成する。これにより、リリースされた ZIP の中身と GitHub 上のタグが一致し、 ローカルの settings.json、生成物、Docker 作業データが混ざらない。

Timeline 側の productRegistry は、将来的に https://github.com/amano0406/<RepositoryName>/releases/latest/download/<RepositoryName>-windows-local.zip を基本 URL として扱う。

段階的な実装方針

  1. 製品レジストリを追加する。
  2. Helper と Worker の製品パス解決をレジストリ経由にする。
  3. 設定ハブで製品が見つからない状態と管理配置を表示する。
  4. 独立した製品管理ページではなく、設定ハブへ統合する。
  5. ローカルパス登録を実装する。
  6. Release ZIP のインストールを実装する。
  7. 更新、アンインストール、整合性チェックを実装する。
  8. 配信サーバー方式を検討する。

今回の実装範囲

  • settings.json に productRegistry を保存できるようにする。
  • 未設定時はデフォルトの製品レジストリを返す。
  • 既存の C:\apps 配置が存在する場合は、互換的にそのパスを使用する。
  • start.ps1 の製品一覧表示を Helper が解決したパスにする。

現行の別作業

以下は設定統合の残作業ではなく、製品配布・更新管理として別途設計する。 削除や上書きを伴うため、確認ダイアログ、操作ログ、失敗時の復旧方針を決めてから実装する。

  • Release ZIP の自動ダウンロード。
  • Git clone による導入。
  • アンインストール。
  • バージョン更新。
  • ライセンス認証や課金連携。
