Timeline サブ製品管理設計（旧案）

この資料はサブ製品管理を検討した初期メモです。現在の実装方針は settings-unification-design.html と settings-unification-todo.md を優先します。 製品をまとめる親ディレクトリ概念は採用せず、製品ごとの管理配置だけを扱います。

Timeline は親製品であり、TimelineForAudio、TimelineForWindowsCodex、 TimelineForChatGPT、TimelineForImage などのサブ製品を利用して時間軸データを構築する。 一般ユーザーが Timeline 本体だけを入れた場合、サブ製品が存在しない可能性が高いため、 サブ製品の場所、導入状態、更新、削除を Timeline 側で管理できる必要がある。

現段階の実装では、インストール方式を GitHub のタグ付き source archive ZIP に寄せる。 製品レジストリを起点に、固定パス依存と独自配布 ZIP 依存を減らす。

目的

  • Timeline 本体が、各サブ製品の導入状態を把握できるようにする。
  • CLI 呼び出し先を固定パスではなく設定から解決する。
  • 既定配置を Timeline のデータルート配下に寄せ、固定パス依存を減らす。
  • 一般ユーザー向けにも、必要に応じて製品ごとの管理配置を設定できるようにする。
  • GitHub source archive ZIP、Git clone、配信サーバー方式へ拡張できる形にする。

製品レジストリ

Timeline の settings.json に productRegistry を持たせる。 これは UI と Helper が参照するサブ製品管理の起点となる。 

{
  "productRegistry": {
    "products": [
      {
        "id": "audio",
        "displayName": "TimelineForAudio",
        "path": "data\\products\\TimelineForAudio",
        "sourceType": "github-source-archive",
        "sourceUrl": "https://github.com/amano0406/TimelineForAudio",
        "version": "",
        "enabled": true,
        "required": false
      }
    ]
  }
}

パス解決ルール

  1. path が存在すれば、それを使う。
  2. path が存在しない場合は、製品が見つからない状態として表示する。
  3. 旧形式の installPath や developmentPath は読み取り時の移行互換だけで扱う。

このルールにより、既定では Timeline のデータルート配下から CLI を呼び出し、 個別上書きが必要な環境では選択した製品配置から CLI を呼び出せる。

サブ製品マニフェスト

製品をインストールした後は、サブ製品ルート直下の timeline-product.json を読んで、起動、停止、CLI、設定ファイル、生成データ、アンインストール時の扱いを解決する。 Timeline 側は、製品ごとの Docker 名や生成データの場所を推測しない。

インストール前はサブ製品のファイルを読めないため、入手元と配置先は引き続き productRegistry で管理する。 インストール後の製品固有情報は timeline-product.json を正とする。

詳細仕様は docs/timeline-product-manifest.md にまとめる。

入手方式の比較

方式 用途 利点 弱点
local 開発・手動配置 既存環境に合わせやすい 一般ユーザーには配置判断が難しい
git 開発者・検証 更新と差分確認が容易 Git 導入やアカウント前提になりやすい
github-source-archive 一般ユーザー初期配布 Git 不要でタグの source ZIP を展開するだけで済む 公開リポジトリとタグ管理が必要
managed-server 将来の収益化・配信管理 ライセンス、バージョン、配布制御を持ちやすい 配信サーバー運用が必要

GitHub source archive の統一ルール

一般ユーザー向けのインストールは Git clone ではなく、GitHub がタグから自動生成する source archive ZIP を優先する。公開リポジトリであれば、通常 GitHub アカウントも Git も不要。 

https://github.com/amano0406/<RepositoryName>/archive/refs/tags/<tag>.zip

ZIP は GitHub が Git タグから作成する。これにより、ZIP の中身と GitHub 上のタグが一致し、 リポジトリに含めていないローカルの settings.json、生成物、Docker 作業データは混ざらない。

独自配布 ZIP は標準配布から外す。チェックサム、署名、ビルド済みバイナリ、 ライセンス別配布が必要になった場合だけ、Release asset として再検討する。

段階的な実装方針

  1. 製品レジストリを追加する。実装済み。
  2. Helper と Worker の製品パス解決をレジストリ経由にする。実装済み。
  3. 設定ハブで製品が見つからない状態と管理配置を表示する。実装済み。
  4. 独立した製品管理ページではなく、設定ハブへ統合する。実装済み。
  5. ローカルパス登録を実装する。実装済み。
  6. GitHub source archive ZIP のインストールを実装する。実装済み。
  7. 更新、アンインストール、整合性チェックを実装する。実装済み。
  8. 配信サーバー方式を検討する。

別環境サンドボックス検証

製品管理のインストール、更新、アンインストールを実ユーザーに近い形で確認するため、 現行の Timeline 製品ディレクトリとデータルートから切り離した検証用 Timeline 環境を作る。 これは通常開発環境ではなく、初回導入体験と削除復元フローを確認するための使い捨て環境である。

  • 検証用 Timeline 本体を、現行リポジトリとは別ディレクトリへ展開する。
  • 検証用の保存先、作業ディレクトリ、サブ製品配置先を専用ディレクトリへ向ける。
  • サブ製品が何もない状態から、製品管理のインストールボタンで導入できるか確認する。
  • 少量のサンプルデータだけを使い、スキャン、一覧、詳細、ダウンロード、アンインストールを確認する。
  • 検証用の実行環境データは削除してよいものとして扱い、現行環境のコンテナ、イメージ、ボリューム、実データとは混ぜない。

ここでの目的は、開発者の既存環境で動くことではなく、 ユーザーが新規に Timeline を入れた時に迷わずサブ製品を導入し、不要になったら安全に削除できることを確認することである。

マスターデータとマイグレーション

サブ製品と Timeline 本体がバージョンアップしていくと、マスターデータや AI 生成物をファイルだけで管理する方式には限界が出る。 実行ファイルやアプリ本体は、停止、削除、再展開、起動で更新できるが、一度作ったデータは同じ扱いにできない。

  • マスターデータ、AI 生成物、言語化結果、OCR 結果、分析結果は、更新時に壊してはいけない。
  • 公開前に、ローカルデータベースとマイグレーションの仕組みを導入するか判断する。
  • データベース製品は未確定。ローカル用途なので SQLite などの組み込み型を第一候補にし、MySQL などは運用上の理由がある場合に検討する。
  • サブ製品ごとに独立したデータベースを持つのか、Timeline 本体が統合データベースを持つのかは別途設計する。
  • JSON や ZIP のファイル出力は、バックアップ、エクスポート、LLM 入力用として残してよい。
  • ただし、更新に耐える正本データにはスキーマバージョンと移行手順が必要である。

目的は、破壊的変更を禁止することではない。 必要な破壊的変更を、ユーザーの既存データを壊さずに適用できる状態にすることである。

今回の実装範囲

  • settings.json に productRegistry を保存できるようにする。
  • 未設定時はデフォルトの製品レジストリを返す。
  • 既定では data\products 配下を製品配置として使用する。
  • start.ps1 の製品一覧表示を Helper が解決したパスにする。

現行の別作業

以下は設定統合の残作業ではなく、製品配布・更新管理として別途設計する。 GitHub source archive ZIP の導入、更新、アンインストールは Timeline 側に実装済み。 今後は配信サーバー方式やライセンス連携など、運用方式の拡張を別途扱う。

  • Git clone による導入。
  • ローカルデータベースとマイグレーション方式。
  • ライセンス認証や課金連携。
  • 配信サーバー方式。
